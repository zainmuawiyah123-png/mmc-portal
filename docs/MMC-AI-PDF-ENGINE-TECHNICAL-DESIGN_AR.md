# MMC AI — التصميم الفني لمحرك PDF وعزل المشاريع
تاريخ المراجعة: 2026-11-10
الحالة: تصميم فني قبل التنفيذ — لا يوجد ادعاء بأن PDF Takeoff أصبح عاملاً.

## 1. نتائج تدقيق المستودع

### الاعتماديات
- خادم Node.js 22 وExpress 4.
- لا توجد حالياً اعتماديات PDF مخصصة في `server/package.json` أو `server/package-lock.json` (لم يظهر pdfjs-dist أو pdf-parse أو pdf-lib أو MuPDF).
- الاعتماديات الحالية تتضمن multer للرفع، better-sqlite3 لقاعدة البيانات، وطبقة تخزين محلية/S3.

### استقبال الملفات
- `server/src/routes/files.js` يوفر رفعاً عاماً لملفات العطاءات عبر `POST /api/tenders/:id/files`.
- هذا المسار يفرض ملكية العطاء للمستخدم عبر `A.ownTender`، ثم يخزن الملف بمفتاح يبدأ من users/<user_id>/tenders/<tender_id>.
- قائمة الامتدادات تسمح PDF وCAD والصور، لكن فحص نوع الملف الحالي يعتمد أساساً على الامتداد، وليس تحليل بنية PDF أو التحقق من توقيع المحتوى.
- هذا المسار ليس واجهة رفع لمشاريع MMC AI، ولا ينبغي إعادة استخدامه مباشرة لملفات المشاريع دون تصميم صلاحيات مستقل.

### الهوية والجهات
- المصادقة الحالية JWT و`users`، مع حارس ملكية فردي للملفات والعطاءات.
- `organizations` و`org_members` موجودتان ضمن سير عمل حسابات المشتريات، كما أن `project_requests` و`request_docs` مرتبطة بجهة مشتريات.
- لا يظهر في البنية الحالية نموذج عام موحد لمشاريع الذكاء الاصطناعي يضم المقاول والاستشاري والمالك وفريق المشروع في مساحة واحدة.
- لذلك لا نفترض أن كل مستخدم لديه `org_id` صالح، ولا نسمح بتحديد tenant من قيمة يرسلها المتصفح وحدها.

### الواجهة
- `webpages/mmc-ai/index.html` واجهة معاينة تصميمية. وجود تبويب للمخططات وحصر الكميات لا يعني وجود API أو محرك PDF فعلي.
- خادم Express يقدم الملفات الثابتة من `WEB_ROOT`؛ يجب التحقق من مسار النسخة المنشورة ومن نقطة دخول الصفحة الرئيسية قبل إضافة أي مسار إنتاجي.

## 2. القرار المعماري المقترح

إنشاء نطاق بيانات مستقل لوحدة MMC AI، مع إمكانية ربطه لاحقاً بمعرّف جهة أو طلب مشروع موجود بعد التحقق من الصلاحيات.

الجداول المقترحة:
1. `ai_projects`: المشروع، المالك/المنشئ، الجهة عند وجودها، البلد، العملة، الحالة.
2. `ai_project_members`: أعضاء المشروع وأدوارهم (owner, project_manager, engineer, quantity_surveyor, reviewer, viewer).
3. `ai_documents`: الملف الأصلي، checksum، storage driver/key، mime بعد التحقق، الحجم، الرافع، المشروع، حالة المعالجة.
4. `ai_drawing_sheets`: صفحات/لوحات المخطط، أرقام الصفحات، metadata، وحدة الرسم، المقياس، حالة المعايرة.
5. `ai_processing_jobs`: إصدار المحرك، نوع المهمة، الحالة، أخطاء المعالجة، أوقات التنفيذ.
6. `ai_takeoff_runs`: إصدار قواعد القياس، إصدار المخطط، المستخدم المراجع، الحالة.
7. `ai_takeoff_items`: نوع العنصر، الهندسة/المراجع، الكمية، الوحدة، المعادلة، الثقة، الافتراضات، حالة الاعتماد.
8. `ai_audit_log`: سجل غير قابل للمحو من المستخدم العادي لكل وصول وتعديل واعتماد وتصدير.

### عزل البيانات
- يستخرج الخادم المشروع المسموح من عضوية المستخدم في `ai_project_members`؛ لا يثق في `project_id` أو `org_id` وحده.
- كل استعلام وقراءة وتنزيل وتعديل وحذف وتصدير يجب أن يكون مقيداً بالمشروع والعضوية.
- صلاحية viewer قراءة فقط؛ وreviewer يعتمد أو يرفض؛ ولا يملك أي دور صلاحية الوصول لمشروع آخر.
- الروابط الموقعة قصيرة العمر، وتصدر بعد فحص العضوية في كل مرة.
- مفاتيح التخزين تكون ضمن مساحة مشروع مع UUID عشوائي، ولا تحتوي أسماء أو بيانات حساسة. تخزن metadata في قاعدة البيانات.
- لا يتم فتح الملفات من روابط عامة أو تقديمها عبر static middleware.
- سجل تدقيق لكل تنزيل ومعالجة وتعديل قياس وتصدير.
- عمليات الحذف تكون soft-delete أولاً، مع سياسة احتفاظ ونسخ احتياطي واضحة.

## 3. خط معالجة PDF المقترح

### المرحلة A — التحقق الآمن من الملف
- التحقق من حجم الملف الفعلي، magic bytes، توقيع PDF، وجود بنية قابلة للقراءة، ورفض الملفات المقنّعة بامتداد PDF.
- تحديد الملفات المشفرة أو التالفة أو التي تتجاوز حدود الموارد؛ لا نحاول تجاوز كلمات المرور.
- عدم اعتبار Content-Type القادم من المتصفح مصدراً موثوقاً.
- فحص الملفات في worker مع حدود CPU والذاكرة والوقت، وليس ضمن طلب HTTP طويل.
- حفظ SHA-256 للملف الأصلي وتسجيل إصدار parser.

### المرحلة B — تحليل PDF المتجهي
اختيار محرك بعد مقارنة تقنية موثقة، مع اختبار:
- استخراج النص ومربعاته وإحداثياته.
- استخراج مسارات الرسم والخطوط والمنحنيات والحدود.
- استخراج الصور المضمنة ومواضعها.
- التحويل بين PDF user space وإحداثيات العرض مع تدوير الصفحة وCropBox/MediaBox.
- الحفاظ على العلاقة بين كل عنصر ورقم الصفحة ومصدره.
- التعامل مع compressed object streams والخطوط والترميزات وملفات متعددة الصفحات.

لا يكفي استخراج النص أو تحويل الصفحة إلى صورة لقياس هندسي دقيق.

### المرحلة C — PDF الممسوح ضوئياً
- كشف الصفحة raster أو hybrid.
- OCR للنصوص والأبعاد مع موضع كل كلمة وثقة القراءة.
- كشف الخطوط والرموز والحدود بصرياً.
- تصحيح الميل والمنظور دون تغيير المقياس الهندسي.
- إعادة معايرة المقياس بعد أي تحويل للصورة.
- لا تدمج نتائج OCR مع هندسة متجهية دون حفظ مصدر كل عنصر.

### المرحلة D — القياس
- المقياس لا يُستنتج من دقة الصورة DPI وحدها.
- يثبت المقياس من dimension موثوق أو نقطتي معايرة يحددهما المستخدم، مع إظهار خطأ المعايرة.
- دعم مقياس مختلف لكل viewport/صفحة عند الحاجة.
- تحويل الوحدات وإظهارها صراحةً.
- كل كمية مرتبطة بمعادلة هندسية قابلة لإعادة الحساب ومصدر واضح.
- عند غموض المقياس أو الحد الهندسي: لا تصدر كمية نهائية، بل حالة Needs Review.

## 4. محرك PDF: اختيار التقنية

لا تُضاف مكتبة قبل Proof of Capability على مجموعة PDF ممثلة. يجب مقارنة محركين على الأقل من حيث:
- دقة استخراج النص والمسارات والإحداثيات.
- دعم Node.js 22 وتشغيل worker منفصل.
- دعم الترخيص التجاري والتوزيع.
- حجم الحزمة والذاكرة والسرعة.
- معالجة ملفات كبيرة/معطوبة بأمان.
- إمكانية إعادة إنتاج النتائج بنفس إصدار المحرك.

يجب توثيق قرار الاختيار والترخيص وتكلفة التشغيل قبل تعديل package.json أو lockfile.

## 5. نموذج البيانات للقياس القابل للتدقيق

كل نتيجة takeoff يجب أن تحفظ:
- project_id, document_id, sheet_id, processing_job_id, takeoff_run_id.
- geometry reference (coordinates/paths) وbounding box.
- source type: pdf_vector | raster_vision | user_manual.
- scale value, scale unit, calibration points, calibration method.
- formula, inputs, output quantity, output unit.
- parser/model/ruleset versions.
- confidence score مع تعريف طريقة حسابه.
- assumptions, exclusions, warnings.
- review_status: proposed | needs_review | approved | rejected.
- reviewer_id ووقت المراجعة وسجل أي تعديل.

## 6. معايير اختبار PDF

مجموعة قبول مستقلة تشمل:
- PDF vector مع خطوط وأبعاد ونصوص واضحة.
- PDF ممسوح 150/300/600 DPI.
- ملفات متعددة الصفحات وتدوير 90/180/270 درجة.
- CropBox مختلف عن MediaBox.
- صفحات بمقاييس مختلفة.
- خطوط عربية/لاتينية وترميزات مختلفة.
- ملفات بها صور ومخططات متجهية معاً.
- ملفات مشفرة وتالفة ومقنّعة وذات حجم كبير.

لكل ملف Ground Truth مُراجع من مهندس، مع قياس:
- نجاح فتح الملف واستخراج العناصر.
- دقة مواقع النصوص والأبعاد.
- precision/recall للعناصر المكتشفة.
- خطأ الكميات لكل بند، لا إجمالي المشروع فقط.
- نسبة الحالات التي تم رفض إصدار كمية لها بسبب عدم كفاية البيانات.
- زمن المعالجة واستهلاك الذاكرة.

## 7. بوابات التنفيذ

1. اعتماد نموذج الصلاحيات والجداول دون تعديل جداول MMC الحالية.
2. تنفيذ migrations idempotent واختبارات عزل مشروعين ومستخدمين متقاطعين.
3. تنفيذ PDF preflight ورفع خاص بـ MMC AI، مع اختبار MIME spoofing وملفات تالفة.
4. تنفيذ PDF vector extraction على عينة مرجعية، دون قياس آلي أولاً.
5. تنفيذ viewer overlay ومعايرة يدوية قابلة للتدقيق.
6. إضافة قياسات محدودة ثم مقارنة النتائج بـ Ground Truth.
7. توسيع OCR والرموز والربط بـ BOQ بعد اجتياز بوابة الدقة.
8. لا merge ولا Render deployment دون موافقة صريحة.

## 8. ما لم يُنفذ بعد
- لا يوجد PDF parser في الاعتماديات الحالية.
- لا يوجد endpoint مستقل لرفع مستندات MMC AI.
- لا توجد جداول ai_projects / ai_documents / ai_takeoff.
- لا يوجد PDF vector extraction أو OCR أو PDF quantity takeoff فعلي.
- هذا المستند مواصفة فنية وتدقيق للموجود، وليس دليلاً على تنفيذ هذه الوظائف.
