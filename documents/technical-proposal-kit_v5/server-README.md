# بوابة العروض الفنية — الخادم (المرحلة الثانية)

المرحلة الأولى بنت خادماً حقيقياً مع قاعدة بيانات ومصادقة.
**المرحلة الثانية تضيف ثلاث قدرات:** تخزين مجرّد يعمل محلياً أو على أي سحابة متوافقة مع S3، وترحيل الملفات الموجودة إلى السحابة، ونسخ احتياطي مجدول مع استعادة مُختبَرة.

---

## ١. المتطلبات

| | |
|---|---|
| Node.js | 20 أو أحدث (اختُبر على 20/22) |
| نظام التشغيل | Linux / macOS / Windows (WSL) |
| مساحة القرص | 200 م.ب على الأقل (بلا ملفات مرفوعة) |
| حساب سحابي | اختياري — النظام يعمل كاملاً بدون أي مفاتيح |

```bash
cd portal-server-v5
npm install
cp .env.example .env      # ثم عدّل القيم
npm run migrate
```

## ٣. الانتقال إلى S3 (متغير واحد)

```bash
# .env
STORAGE_DRIVER=s3
S3_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
S3_REGION=auto
S3_BUCKET=tpkit-files
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_FORCE_PATH_STYLE=true
```

ثم أعد تشغيل الخادم وافحص:

```bash
curl -s localhost:4000/api/health/storage | python3 -m json.tool
```

يجب أن ترى `"ok": true` و`"configured": "s3"`.

### إعداد Cloudflare R2 خطوة بخطوة

1. **أنشئ المجلد:** لوحة R2 → *Create bucket* → الاسم `tpkit-files` → الموقع الجغرافي الأقرب (مثلاً *Middle East*).
2. **أنشئ مفتاح API:** R2 → *Manage R2 API Tokens* → *Create API token* → الصلاحية **Object Read & Write** → حدّده على هذا المجلد فقط.
3. **خذ القيم الأربع:** `Access Key ID`، `Secret Access Key`، و`<ACCOUNT_ID>` من عنوان اللوحة، واسم المجلد.
4. **اضبط `.env`:**
   ```
   S3_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
   S3_REGION=auto
   S3_FORCE_PATH_STYLE=true
   ```
   ⚠️ `auto` هو region الصحيح لـ R2، و`forcePathStyle=true` إلزامي (R2 لا يدعم النطاق الفرعي للمجلد).
5. **لا تفعّل الوصول العام على المجلد.** كل التحميل يمر عبر روابط موقّعة قصيرة الصلاحية، والوصول العام يلغي فائدة ذلك.
6. **اختبار:** `curl -s localhost:4000/api/health/storage` ثم ارفع ملفاً من البوابة وتأكد من ظهوره في لوحة R2 تحت `users/<user_id>/tenders/<tender_id>/`.

### إعداد AWS S3

| المتغير | القيمة |
|---|---|
| `S3_ENDPOINT` | اتركه **فارغاً** (يُستنتج من المنطقة) |
| `S3_REGION` | `eu-west-1`, `me-south-1`, … (منطقة المجلد الفعلية) |
| `S3_FORCE_PATH_STYLE` | `false` (AWS يدعم virtual-hosted) |

المستخدم (IAM) يحتاج فقط: `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket` على هذا المجلد.

### إعداد MinIO (محلي / خاص)

```bash
docker run -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  minio/minio server /data --console-address ":9001"
```

```
S3_ENDPOINT=http://127.0.0.1:9000
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=true
```

## ٤. طبقة التخزين المجرّدة

كل المشغّلات تنفّذ نفس العقد، فالواجهة لا تتغير بينها:

```
put(key, buffer, meta)  → { key, driver, size, checksum }
get(key)                → Buffer
stream(key)             → Readable
delete(key)
exists(key)             → boolean
signedUrl(key, opts)    → { url, expiresIn, driver }
health()                → { ok, driver, detail }
deletePrefix(prefix)    → عدد المحذوفات
```

| المشغّل | الملف | الرابط الموقّع |
|---|---|---|
| `local` | `src/lib/storage/local.js` | رمز HMAC قصير العمر يُتحقَّق محلياً |
| `s3` | `src/lib/storage/s3.js` | presigned GET من AWS SDK v3 |

**مفتاح التخزين منظّم دائماً:**
```
users/<user_id>/tenders/<tender_id>/<32-char-hex>.<ext>
```

اسم التخزين عشوائي ولا يحتوي اسم الملف الأصلي — يمنع تصادم الأسماء وكشف المعلومات.

### ما يُسجَّل لكل ملف في قاعدة البيانات

| الحقل | المعنى |
|---|---|
| `storage_key` | المفتاح داخل المشغّل |
| `storage_driver` | `local` أو `s3` — يسمح بوجود النوعين معاً أثناء الترحيل |
| `checksum_sha256` | تجزئة المحتوى — أساس كل تحقق |
| `migrated_at` | وقت الترحيل الناجح إلى السحابة |
| `size`, `mime`, `category` | كما في المرحلة الأولى |

**ملاحظة مهمّة:** الحقل `storage_driver` يُقرأ لكل ملف على حدة عند التحميل. لذا أثناء الترحيل — أو بعده لو بقي ملف لم يُنقل — يستمر الملف القديم في العمل من القرص بينما الجديد يعمل من السحابة. لا انقطاع.

## ٥. ترحيل الملفات الموجودة إلى السحابة

```bash
# معاينة بلا أي رفع — اطبع ما سيحدث
node scripts/migrate-to-cloud.js --dry-run

# الترحيل الفعلي
node scripts/migrate-to-cloud.js

# الترحيل ثم حذف النسخ المحلية بعد التحقق
node scripts/migrate-to-cloud.js --delete-local

# جرّب على ٥ ملفات فقط
node scripts/migrate-to-cloud.js --limit=5
```

يتطلب `STORAGE_DRIVER=s3`؛ يرفض العمل بغيره ويرجع بالخطأ 1.

### الضمانات

- **idempotent** — إعادة التشغيل لا ترفع ما رُفع بالفعل. الملفات التي `migrated_at` غير فارغ تُستثنى.
- **تحقق مزدوج** — بعد الرفع يُنزَّل الكائن من السحابة ويُقارن SHA-256 مع الملف المحلي. لا يُحدَّث الصف في قاعدة البيانات إلا بعد تطابق التجزئتين.
- **لا حذف تلقائي** — `--delete-local` صريح، ويحدث بعد التحقق فقط.
- **فحص مسبق للسلامة** — إن كان `checksum_sha256` مسجّلاً ولا يطابق المحتوى المحلي، يُعتبر الملف تالفاً ولا يُرفع.
- **تقرير كامل** — كل ملف يُسجَّل في `backups/migration-reports/migrate-<timestamp>.json` وفي `audit_log`.
- **خروج برمز** — `0` نجاح تام، `2` بعض الملفات فشلت، `1` خطأ فادح (خدمة غير متاحة).

## ٦. النسخ الاحتياطي

```bash
node scripts/backup.js                  # نسخة كاملة (VACUUM INTO + gzip + رفع)
node scripts/backup.js --local-only     # بلا رفع للسحابة
node scripts/backup.js --no-retention   # بلا تطبيق سياسة الاستبقاء
```

### لماذا `VACUUM INTO` وليس `cp`

نسخ ملف SQLite بـ `cp` أثناء عمل الخادم يلتقط حالة **غير متسقة**: صفحات نصف مكتوبة، وملف WAL غير مُدمَج. النتيجة قاعدة تبدو سليمة حتى تحاول قراءتها. `VACUUM INTO` يطلب من SQLite نفسه كتابة نسخة متسقة داخل معاملة قراءة واحدة — آمنة تماماً والخادم يعمل. **الكود لا يستخدم `fs.copyFile` إطلاقاً.**

### المسار الكامل

1. `VACUUM INTO` ملف مؤقت.
2. **تحقق:** يُفتح الملف المؤقت، يُشغَّل `PRAGMA integrity_check`، وتُقارن أعداد الصفوف في كل جدول مع القاعدة الأصلية. أي اختلاف ← تُلغى النسخة ويُرمى خطأ.
3. `gzip` بمستوى 9 + SHA-256 للملف المضغوط والأصلي.
4. ملف بيان `.json` بجانب النسخة يضم التجزئتين وأعداد الصفوف.
5. رفع إلى `backups/db/YYYY/MM/` **ثم تنزيل والتحقق من التجزئة** قبل اعتبار الرفع ناجحاً.
6. سياسة استبقاء (محلياً وسحابياً): **آخر ٧ يومية + ٤ أسبوعية + ١٢ شهرية**.
7. سجل في `backups/backup.log` + `audit_log` (النجاح والفشل كلاهما).

### الجدولة التلقائية

```bash
SCHEDULER_ENABLED=true
BACKUP_CRON=30 2 * * *        # 02:30 كل يوم
BACKUP_TZ=Asia/Riyadh
```

التعطيل بمتغير واحد: `SCHEDULER_ENABLED=false`. لا حاجة لتعديل الكود.

الجدولة تعمل داخل الخادم بـ `node-cron`، لكن كل نسخة تُنفَّذ في **عملية فرعية معزولة** — خطأ في النسخ لا يُسقط الخادم. كل تشغيل يُسجَّل في `backups/scheduler.log`:

```
[2026-10-21T13:40:00.316Z] OK   backup  311ms  portal-20261021-134000.db.gz 3.5KB
```

الحالة ظاهرة أيضاً في `GET /api/health` تحت `scheduler`.

## ٧. الاستعادة

```bash
node scripts/restore.js --list                                    # اعرض النسخ المتاحة
node scripts/restore.js --latest --to=./data/restored.db          # استعد إلى ملف جديد (آمن)
node scripts/restore.js --file=portal-20261021-023000.db.gz --to=./data/restored.db
node scripts/restore.js --latest --in-place --yes                 # استبدل القاعدة الحالية (خطِر)
```

### ما تفعله

1. تتحقق من SHA-256 للملف مقابل البيان **قبل** أي فك ضغط. تالف ← توقف فوري.
2. تفك الضغط وتتحقق من تجزئة الناتج أيضاً.
3. تكتب في ملف مؤقت ثم تنقل — لا قاعدة نصف مكتوبة عند الانقطاع.
4. تفتح النسخة وتُشغّل `integrity_check`.
5. **تطبع جدول مقارنة** لكل جدول: عدد الصفوف في البيان مقابل المستعاد، مع ✓/✗.
6. عند `--in-place` تأخذ **نسخة أمان** من القاعدة الحالية أولاً (`portal.db.before-restore-<ts>`).
7. ترجع `0` إن نجح كل شيء، `3` إن نجحت الاستعادة لكن التحقق فشل.

`--in-place` بدون `--yes` يُرفض. لا استبدال صامت.

## ٨. نقاط API الجديدة والمعدَّلة

| الطريقة | المسار | الوصف |
|---|---|---|
| `GET` | `/api/health` | الحالة العامة + مشغّل التخزين + حالة الجدولة |
| `GET` | `/api/health/storage` | فحص حقيقي للاتصال بالسحابة (`ok`/`detail`) |
| `POST` | `/api/tenders/:id/files` | رفع عبر الطبقة المجرّدة، يعيد `driver` و`checksum` |
| `GET` | `/api/tenders/:id/files` | القائمة + `driver` لكل ملف |
| `GET` | `/api/files/:id/url` | **رابط موقّع** بصلاحية `SIGNED_URL_TTL` |
| `GET` | `/api/files/:id/download` | تحميل محمي (يتحقق من الملكية) |
| `GET` | `/api/storage/local` | مسار التحميل للرابط المحلي الموقّع |
| `DELETE` | `/api/files/:id` | حذف من قاعدة البيانات **ومن التخزين** |

كل نقاط الملفات تتحقق من الملكية أولاً. مستخدم يطلب ملف غيره يحصل على **404** لا 403 — لا نكشف حتى وجود المعرّف.

### سجل التدقيق

كل عملية تُسجَّل في جدول `audit_log`: `action` (`upload` / `download` / `signed_url` / `delete` / `backup` / `restore` / `migrate`)، `entity`، `user_id`، `driver`، `ip`، و`detail` بصيغة JSON. فشل التسجيل لا يُفشل الطلب الأساسي.

```sql
SELECT at, action, entity, driver, ok FROM audit_log ORDER BY id DESC LIMIT 20;
```

## ١٠. استكشاف الأخطاء

| الأعراض | السبب | الحل |
|---|---|---|
| `504` أو `ECONNREFUSED` عند الرفع | `S3_ENDPOINT` خاطئ أو الخدمة متوقفة | `curl $S3_ENDPOINT` — ثم `/api/health/storage` |
| `403 SignatureDoesNotMatch` | مفتاح أو سر خاطئ، أو region خاطئ | تحقق من المفاتيح؛ R2 يحتاج `S3_REGION=auto` |
| `404 NoSuchBucket` | المجلد غير موجود أو اسمه خاطئ | أنشئه — السكربت لا يُنشئ المجلدات تلقائياً |
| `403` مع R2 أثناء العمل | `S3_FORCE_PATH_STYLE=false` | اضبطه على `true` |
| الرابط الموقّع ينتهي بسرعة | `SIGNED_URL_TTL` قصير | ارفعه إلى 600 كحد أقصى — لكن الأفضل إعادة الطلب |
| `EACCES` في النسخ الاحتياطي | صلاحيات `BACKUP_DIR` | `chown` للمستخدم الذي يشغّل الخادم |
| الجدولة لا تعمل | `SCHEDULER_ENABLED=false` أو cron غير صالح | تحقق من `GET /api/health` → `scheduler` |
| `WEB_ROOT غير موجود` عند الإقلاع | المسار الافتراضي لا يطابق مكان الحزمة | اضبط `WEB_ROOT` صراحةً |
| الخادم يرفض الإقلاع في الإنتاج | `JWT_SECRET` افتراضي | ولّد سراً جديداً في `.env` |
| استعادة تفشل بفحص التجزئة | النسخة تالفة | جرّب نسخة أقدم — `node scripts/restore.js --list` |

## ١١. ⚠️ ما لم يُختبر على سحابة حقيقية — بصراحة

هذا القسم الأهم في هذا الملف. **لم يُشغَّل النظام على AWS S3 ولا Cloudflare R2 فعلياً** — لا يوجد حساب سحابي في بيئة التطوير هذه.

### ما اختُبر فعلاً

| الاختبار | النتيجة | كيف |
|---|---|---|
| مشغّل S3 كامل (رفع/تنزيل/حذف/فحص/قائمة) | ✓ نجح ١١/١١ | `s3rver` — خادم HTTP يحاكي S3 فعلياً على الشبكة، وليس mock في الذاكرة |
| توقيع الروابط الموقّعة بصلاحية قصيرة | ✓ البنية والصلاحية صحيحة | AWS SDK يوقّع الرابط، و`X-Amz-Signature` موجود |
| التحقق من التجزئة بعد الرفع | ✓ مطابق تماماً | تنزيل فعلي ومقارنة SHA-256 |
| العزل بين المستخدمين | ✓ ٤٠٤ في كل الحالات | ٦ حالات عبور |
| الترحيل | ✓ ٤ ملفات، تجزئات مطابقة، idempotent | تشغيلان متتاليان |
| النسخ الاحتياطي والاستعادة | ✓ ٧ جداول متطابقة | مقارنة صفوف جدولاً بجدول |
| سياسة الاستبقاء | ✓ ٣٠ → ١٠ ملفات فريدة | ٧ يومية + ٤ أسبوعية + ١٢ شهرية، مع إزالة التكرار |
| الجدولة التلقائية | ✓ عملت وحدها وأنتجت نسخة مرفوعة | `*/5 * * * *` |

### ما لم يُختبر — والفرق المهم

**`s3rver` خادم محاكاة، لا S3 حقيقي.** الاختبارات أثبتت أن **كودنا** يعمل: المسارات، التوقيع، التجزئات، العزل، الحذف. لكنها **لا تثبت** سلوك AWS/R2 في أربعة أمور:

1. **فرض انتهاء صلاحية الروابط.** `s3rver` لا يتحقق من `X-Amz-Signature` ولا `X-Amz-Expires` إطلاقاً — أي رابط مقبول. AWS S3 و R2 يفرضان الاثنين بـ 403. **فرض التوقيع والانتهاء اختُبر فقط على مشغّل القرص المحلي** (HMAC نتحكم فيه بالكامل، ٥ حالات عبور) — وهو مكان منطق مشابه لكنه ليس نفس التنفيذ.
2. **CORS وسياسات الـ bucket.** لا تُحاكى. إن كنت ستفتح الملفات مباشرة من المتصفح عبر نطاق آخر، ستحتاج ضبط CORS على المجلد.
3. **حدود الخدمة والتسعير.** لا شيء عن عدد العمليات، الحجم، أو التكلفة.
4. **`ChecksumSHA256`.** يُرسل مع كل رفع، لكن `s3rver` يتجاهله. AWS يتحقق منه فعلياً وقد يرفض رفعاً تالفاً — سلوك لم نرَه.

### ما أوصي به قبل الإنتاج

```
١. أنشئ مجلداً تجريبياً على R2 أو S3 (ليس الإنتاجي).
٢. شغّل npm run test:s3 مع S3_TEST_ENDPOINT على عنوان R2 الحقيقي.
٣. اختبر يدوياً: افتح رابطاً موقّعاً بعد انتهاء مدته ← يجب 403.
٤. شغّل ترحيلاً بـ --dry-run على بيانات حقيقية، ثم بلا --delete-local.
٥. نفّذ نسخة احتياطية واستعدها إلى قاعدة منفصلة، وقارن.
٦. فقط بعد ذلك فعّل SCHEDULER_ENABLED=true على الإنتاج.
```
